# 10〜12：出す段階

## 10. 性能テスト・E2E

### 性能
- 測る前に、目標値（5 で決めた p95、起動時間、メモリ、費用）と、測る条件（データ量、同時接続、端末、ネットワーク、ウォーム／コールド）を書く
- 負荷をかける側が先に限界に達していないかを確かめる。1回の値でなく、複数回の分布（p50・p95）で見る
- 目標内なら直さず、条件と結果を残す。目標外なら原因を測ってから直す（推測で最適化しない）
- 最初の1回が遅い（コールドスタート）、件数が増えると遅くなる、など、条件で変わるものは条件ごとに測る
  出典: Vault の `06-Personal/github-pr-issue-lessons-2026-10.md`（job-match-analysis Issue #82・#83 の測り方）

### E2E
- 3 で決めた主な利用者の流れを、端から端まで自動で通す（Web は Playwright、iOS は XCUITest など、リポジトリの既存の道具に合わせる）
- 正常な流れに加えて、失敗の流れ（通信が切れる、権限が無い、外部サービスが落ちる）を最低1つ
- 実機でしか確かめられないもの（カメラ、通知、画面ロック、容量不足）は、手で確かめる手順を書き、やったかどうかを報告に残す

## 11. リリース
- **順序**：依存する側から出す（例：DB の migration → サーバや Edge Function → アプリ）。古い版のアプリと新しいサーバが同時に動いても壊れないか
- **段階**：一部の利用者・社内・TestFlight などから広げられるか。機能フラグで隠せるか
- **戻し方**：戻す手順と、戻せないもの（データの移行）を先に書く
- **確認**：外への公開・本番への反映・ストアへの提出は、必ず本人の承認を得てから（`dev-judgment` §4）。マージしただけでは本番に出ないリポジトリもある
- **出したあと**：「デプロイできた」と「目的どおりに動く」は別。版・ログ・指標で新しい版が動いていることを確かめる
  出典: Vault の `01-Engineering/Gojuon-Quality-and-Release.md`

## 12. 運用
- **検知**：障害に、利用者より先に気づけるか（エラー率、遅さ、ジョブの滞留、費用）。通知が多すぎて無視されないか
- **切り分け**：外部サービスの失敗と自分の失敗、ページ固有の失敗と全体の失敗を、ログと表示で分けられるか。ログに個人情報を出さない
- **利用者への見せ方**：止まっているのか、終わったのか、待てばよいのかがわかる表示。復旧時に一斉に再接続して負荷が集中しないか
- **回収**：途中で止まった処理が、次の依頼を待たずに回収されるか
- **学びを戻す**：利用者の反応・計測・障害を、1（課題を探す）の材料として Issue に戻す。3 で決めた指標で、効果があったかを確かめ、無かったら理由を残す
  出典: Vault の `06-Personal/operations-costs-and-failure-learning.md`、`06-Personal/github-pr-issue-lessons-2026-10.md`（job-match-analysis Issue #85）
