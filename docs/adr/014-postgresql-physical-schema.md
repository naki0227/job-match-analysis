# ADR-014: PostgreSQLの物理DDLと削除境界

## 背景と課題

Issue #14では[論理ER図](../database.md)を実行可能なDDLにし、個人データ・共有評価・出典の整合性と削除経路を明示する必要がある。出典本文の保持とRLSの導入順序もDDLに影響する。

## 選択肢

- UUIDの実体PK、関連表の複合PK、個人所有行のCASCADE、共有参照のRESTRICT、所属と出典の複合FK。勤務地・必須条件結果は子テーブル。全表RLSを有効化し、ポリシーは次Issueで追加する。
- 連番PKと明示的な全行削除手順、DB関数・トリガー中心の整合性検査。小さな索引を使えるが、削除と整合性の経路が複雑になる。
- 出典本文を保存せず、hashと短い根拠だけを保持する。保存量は小さいが、取得時の評価入力を後から確認しにくい。

## 採用した案と理由

ユーザーの承認により最初の案を採用。出典本文も保存し、取得から30日後に予定済みのworkerで本文列をNULLにする。hash・取得日時・評価に紐づく短い根拠は保持する。workerの接続前は自動削除されないため、本文保存の運用開始条件にする。新しい定期実行サービスは導入しない。

## メリット

- FKとCHECKでユーザー/プロフィール版、求人/会社、評価/出典の不整合をDBで拒否できる。
- UUIDと複合PKにより各実体と関連を明確に区別できる。
- RLSを先に有効化し、Issue #15までクライアントアクセスを閉じられる。
- 本文削除後も参照元のhashと短い根拠を残せる。

## デメリット

- UUID索引と子テーブルのJOINにコストがかかる。
- RLSポリシー追加までクライアントから新規表を利用できない。
- workerが実装されるまで30日削除は自動化されない。評価根拠の短い抜粋は評価が残る間保持される。
- rollbackは追加した全表と行を削除するため、本番適用後はバックアップと移行手順が必要。

## 見直し条件

EXPLAINで索引の不足が判明した場合、個人データの削除・保持要求が変わった場合、または会社/求人の同一性仕様が確定した場合は、新しいmigrationで変更する。既存の評価版やプロフィール版は黙って読み替えない。

## 実装状況（Issue #22）

既存Crawler workerの各周期で30日経過本文を件数上限付きでNULLにする処理を接続した。新規の定期サービスは追加していない。worker停止中の削除遅延と周期は運用設定で管理する。
