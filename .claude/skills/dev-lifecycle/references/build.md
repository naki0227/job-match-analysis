# 5〜9：作る段階

## 5. 制約・条件・状況を確かめる

機能の要求とは別に、数字や事実で書く。書けないものは「未確認」とし、本人しか知らないものは戻す（`dev-judgment` §3）。
- **費用**：月の上限、無料枠、量が増えたときの増え方。前提と時点を書く
- **障害**：どこまでの障害を許さないか（どの部分が、どれくらい止まってよいか）、戻すまでの目標時間
- **性能**：応答の目標（p95 など）、データ量、同時に使う人数、端末の容量や電池
- **プライバシー・安全**：扱う個人情報、外に送る情報、認可の境界。手元で持てるなら手元で持つ
- **期限と人**：いつまでに、だれが運用するか
- **今の状況**：既存のコード・データ・CI・依存・利用者。互換を壊さないこと、移行が要るか

出典: Vault の `06-Personal/operations-costs-and-failure-learning.md`（構成を決める前に費用と障害の許容範囲を数字にしなかった反省）

## 6. どうやって作るか
- 技術と版は `dev-judgment` の `references/tech-selection.md`（候補を広く洗い出す、最新の安定版、一次資料で確かめる）
- 設計の既定値は `dev-judgment` の `references/defaults.md`（既存の仕組みを先に探す、曖昧な処理と決定的な処理を契約で分ける、境界を型とテストで守る、失敗は許可側に倒さない）
- 5 の制約ごとに、それをどう満たすかを1行で書く。満たせない制約があれば、ここで戻す
- 大きな判断は ADR に残す

## 7. 形を作る
実装の前に、考えが合っているかを安く確かめる。作るものに合わせて選ぶ。
- 画面：骨組み（モック、ワイヤー、静的な HTML）。Web なら `site-skills` のスキル、iOS アプリ・ゲームなら `app-quality-bar` を使う（題材の世界観を部品にする・前に作ったアプリの見た目を使い回さない）
- API・データ：契約（エンドポイント、スキーマ、エラー）を先に書き、型やテストの形にする
- 不確かな技術：最小の試作（スパイク）で、動くか・測れるかを確かめる。試作は捨てる前提で、本実装に流用しない
- 体験：一番大事な流れを、手で触れる形にして通してみる

確かめること：3 の影響が出そうか、2 の前提が崩れていないか、5 の制約を満たせそうか。崩れたら前の段階に戻る（戻るのは失敗ではない）。

## 8・9. 実装とテスト
`dev-workflow` の手順に従う。テストは 3 で決めた「何が保証されれば解決したと言えるか」から書き、実装の写しにしない。
