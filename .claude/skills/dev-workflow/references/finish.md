# 終わりの手順（「完了」と言う前）

## 1. 差分をレビュアーとして読む
```sh
git status --short; git diff --stat origin/main...HEAD; git diff origin/main...HEAD   # main は既定ブランチの名前に合わせる
git diff   # まだコミットしていない変更
```
- 意図しない整形、生成物、ついでの修正、デバッグ出力、秘密情報が混ざっていないか
- 変えた箇所以外に、同じ規則が関わる経路が無いか（似た箇所も直すべきか、直さないならなぜか）
- 名前・置き場・エラーの扱い・ログが、周りの既存コードと合っているか
- コメントは「なぜ／なぜ別の方法ではないか」だけ。コードを言い換えただけのコメントを消す

## 2. 反例で壊す
- 足したテストが、誤った実装で本当に落ちるか（一時的に実装を壊して確かめる。確かめたら戻す）
- 境界値、空、不正な入力、権限が無い・他人のもの、同時に来たとき
- 安全性・fail-closed を言うなら、紛らわしい設定や入力でバイパスできないか

## 3. チェックを回す
対象のテスト → 関係するテスト → format → lint → 型・静的解析 → build。CI と同じコマンドを使う。
- 結果は**コマンドと成否**で書く。警告が残るなら「テストは通過、警告 N 件」と分けて書く
- 落ちたら、自分の変更が原因か、もとから落ちていたか（始めに記録したもの）を分ける
- 回せなかったチェックは「未実行（理由）」と書き、通ったことにしない

## 4. 状態の言葉を取り違えない

| 書いてよい言葉 | 意味 | 言えないこと |
|---|---|---|
| 未着手 / Issue に記録 | 問題や計画を書いただけ | 対応済み |
| 実装した | コードを書いた。テストは別 | 動く、直った |
| テスト通過（コマンド） | そのコマンドが成功した | 警告なし、本番で動く |
| PR を出した / マージされた | コードが入った | 公開済み、検証済み |
| 検証した（何で・どこで） | 実機・ブラウザ・計測で確かめた | ほかの環境でも同じ |
| デプロイした | 新しい版が置かれた | 目的どおりに処理できる（ログやメトリクスで別に確かめる） |
| 公開した | 利用者に届く状態 | — |

## 5. 記録する
- **作業報告書・Todo**：このリポジトリの方式（`docs/reports/`、`TODO.md`、Issue など）があればそれに従う。無ければ増やす前に、本当に要るか考える（小さな作業に形だけの報告書を作らない）
  - 報告書：実測の日時（`date '+%Y年%m月%d日 %H時%M分%S秒'`）、目的、変えたファイルと理由、判断（`dev-judgment` §6 の形）、確認したコマンドと結果、やっていないこと、次に最初に読むもの
  - Todo：未着手・進行中・完了・保留・要確認を分ける
- **ADR**：大きな判断（技術の選定、境界の変更、互換を壊す変更）だけ
- **Vault**：別の作業でも役立つ学び（判断とその理由、採らなかった案、不具合やレビューの教訓）があれば、`CLAUDE.md` の手順で既存ノートを更新して PR にする。無ければ「Vault更新なし（理由）」

## 6. 最終報告
```
変更: 〈何を、なぜ〉
確認: 〈コマンド〉 → 成功 / 失敗（〈要点〉）
未実施: 〈何を〉（〈理由〉）
判断: 〈AI が決めたこと〉 — 〈理由〉（詳しくは PR / 報告書）
リスク・残り: 〈…〉
次: 〈…〉
Vault: 〈参照・更新したノート／更新なし（理由）〉
```
必須のチェックが失敗・未実行なら、「完了」と書かずに、その理由と残るリスクを書く。
