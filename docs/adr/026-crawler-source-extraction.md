# ADR-026: 公開求人ページの取得ポリシーと本文抽出

## 背景・課題

Issue #21ではHTTP取得で十分な本文が得られない場合だけブラウザを使う。公開表示、robots、サイトの利用条件は別の判断であり、単にHTTPSで届くことを取得許可と扱えない。会社共通属性を求人固有属性と混ぜると後続の共有評価を誤らせる。

## 選択肢

1. HTTPとブラウザを毎回使い、ページ全文を1つの本文にする。実装は単純だが費用と誤分類が増える。
2. HTTPの求人本文が100非空白文字以上なら採用し、不足時だけPlaywrightを1回使用する。会社と求人は明示的なDOM領域で分ける。
3. サイト専用抽出器を先に作る。精度を上げやすいが、利用サイトが未確定の段階では過剰な保守対象になる。

## 決定と理由

2を採用する。100文字は#9のfixtureで使った暫定閾値を固定した`html-v1`の仕様とし、実ページ評価で版を上げて見直す。`data-job`、JobPosting、`main`の順に求人領域を選び、会社は`data-company`またはOrganizationとして明示された領域だけを抽出する。会社を推測できない場合は空欄にする。抽出本文の正規化結果からSHA-256を作る。出典位置はDOM領域と元HTMLの行番号で保持する。

取得前には`robots.txt`の対象パスを評価する。robotsを取得できない場合、403/429/5xx・通信失敗では取得を保留する。redirect先とブラウザの各要求も同じ判定を通す。robotsの別origin redirectは、確認できないものとして保留する。認証フォーム、非HTML、HTTP失敗はブラウザで回避しない。サイト利用条件の手動承認を必須とした当初の判断はADR-034で変更した。

HTML解析にはlockfileに既存の`parse5@8.0.1`をCrawlerの直接依存として追加する。HTMLの不完全な構造にも対応でき、ブラウザを起動せず静的本文を扱える。依存更新の保守は必要だが、自作HTMLパーサーより誤抽出を減らせる。

## メリット・デメリット・見直し条件

ブラウザ起動を抑え、会社情報の誤った共有を避けられる。一方で明示的な領域がないサイトや厳しいrobotsでは`unknown`が増える。取得頻度、実サイトでの抽出精度、引用範囲を運用前に確定する。SourceDocumentは既存の`commit_analysis_evaluation`で評価と同一TXに保存するため、#22のworker結合時に実保存を確認する。本文30日削除workerの接続前に実サイトの保存運用を開始しない。

## 実装状況（Issue #22）

HTTP/Browser取得からFake DecisionEngine、文書版・8軸評価のDB保存までローカルPostgreSQLで検証した。30日後の本文削除はworker周期に接続した。実サイトごとの引用・個人情報の検証は運用前に行う。
