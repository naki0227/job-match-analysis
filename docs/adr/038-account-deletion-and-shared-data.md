# ADR-038: アカウント削除で消す個人データと残す共有データ

## 背景・課題

Issue #29では、ユーザー削除時に個人の結果をどう消し、複数ユーザーで共有する企業・求人評価をどう扱うかを定義する必要がある。個人データは本人のプロフィール・Match・分析依頼・公開リンクなどに分かれ、共有データは公開ページから作った評価であり特定の個人に属さない。

## 選択肢

1. `auth.users`の削除から外部キーのCASCADEで個人データを一括削除し、共有データは残す。1回の削除で漏れなく消せるが、法的確認履歴も消える。
2. 個人データを匿名化して残す。集計に使えるが、匿名化の妥当性と同意（#40）が必要。
3. 共有評価も依頼者ごとに消す。共有評価は他ユーザーも使うため整合が崩れる。

## 決定（現時点の実装）

1を採用する。`profiles`は`auth.users`に、個人の表はすべて`profiles`（またはその子）に`on delete cascade`で連なる。削除されるのは、プロフィール（任意項目・学歴）、法的文書の確認履歴、希望条件の全版（職種・8軸・必須条件）、Match（軸・必須条件の明細）、公開リンク（`match_shares`）、本人の分析依頼（`user_analysis_requests`）。公開リンクは削除と同時に読めなくなる。

残すのは企業・求人・取得URL・取得文書のメタデータ・共有評価・根拠抜粋・解析ジョブ。いずれも利用者IDを持たず、公開ページ由来の情報である。取得本文は既存方針どおり取得から30日で消す。

この挙動は`supabase/tests/issue29_security.sql`で、別ユーザーのデータと共有データを残したまま対象ユーザーの行が0件になることとして検証する。同じテストで、全表のRLS、クライアントロールに許すSELECTの許可リスト、公開関数を実行できないこと、別ユーザーの親子行が見えないことも確認する。

## 未決定（ユーザー判断が必要）

- 本人がアプリから退会する経路（APIからSupabase Authの管理APIで`auth.users`を削除する）はまだない。設定画面の「データの書き出し・削除」は未接続のまま。
- 法的文書の確認履歴を退会後も一定期間保持する必要があるか。保持する場合は利用者IDを切り離した別表へ移すなど、CASCADEの例外を設計する。
- ログ基盤（#32）導入後の個人データを含まないログの保持期間。

## メリット・デメリット

削除の範囲がスキーマで決まり、表を追加しても`profiles`へのCASCADEを付ければ漏れにくい。CIのテストが新しい個人表の追加漏れ（権限・RLS）も検出する。一方、削除は取り消せず、確認履歴も消える。バックアップ（#31）には削除前のデータが保持期間中残る。

## 見直し条件

退会APIを実装する時、法的保持の要件が決まった時、個人データの集計（#40/#41）を始める時。
