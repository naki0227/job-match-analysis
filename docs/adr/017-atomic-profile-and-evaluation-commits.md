# ADR-017: プロフィール確定と評価完了の原子的保存

## 背景と課題

Issue #16では、プロフィール版とその子行、文書版と評価・根拠・ジョブ完了をそれぞれ一度に確定する。Supabase JSの連続した書込は別トランザクションになり、失敗時に部分確定し得る。FetchとJevの処理時間中はDBトランザクションを保持しない。

## 選択肢

- PostgreSQL関数をSupabase RPCで呼ぶ: 既存のSupabase接続を使い、1呼出しを1トランザクションにできる。関数内の検証と権限管理が必要。
- アプリからPostgreSQLへ直接接続する: 通常のトランザクションを記述しやすいが、接続管理と新規ライブラリが必要。
- 複数RPCを補償処理でつなぐ: 実装は分散しやすいが、完了行と子行の原子性を保証しにくい。

## 決定

ユーザーがIssue #16の設計案Aをすべて承認。SECURITY INVOKERのPostgreSQL関数2つをservice_role専用にする。サーバーのみがSupabase RPCを呼び、ブラウザーには関数実行権限を与えない。

commit_career_profileはプロフィール所有者行をロックし、期待する最新版番号と冪等キーを検査する。版・希望職種・8軸・必須条件を同じトランザクションで保存する。同じキーかつ同じ内容の再送は既存版を返し、内容差と古い版は拒否する。冪等キー列は既存版に対してNULLを許す。

commit_analysis_evaluationはworker tokenでrunning jobを確認し、対象行をロックして評価の自然キーによる重複を直列化する。新規なら文書版・評価・参照・8軸・根拠・job完了を一度に保存する。別jobから同じ自然キーを使うときは、文書・軸・根拠を含む内容が一致した場合にのみ既存評価を再利用する。完了済みの同じjob/tokenの再送は保存済み評価IDを返す。本文が30日後に削除されても、この再送は成立する。別jobによる再利用は削除済み本文との完全比較ができなければ拒否する。

analysis_jobsにはcompleted時のevaluation_id必須制約を加える。文書取得とJev呼出しはこれらの関数の外で行う。URL受付、job claim、個人Match保存はそれぞれ後続Issueの境界とする。

## メリット・デメリット

一回のRPCで部分確定を防ぎ、行ロックと一意制約で競合を扱える。既存の接続方式を使える。一方、SQL関数の入力形式をworker/APIと合わせる必要があり、複雑な保存手順がDBに入る。評価対象ごとの行ロックにより、同じ対象への同時完了は直列化される。

## 見直し条件

大量の同時評価で対象行ロックがボトルネックになった場合、評価本文の保持期間を変える場合、または保存する評価構造を変える場合に見直す。後続のAPI/worker実装ではRPCの入力形式と失敗時のHTTP変換を別途確認する。
