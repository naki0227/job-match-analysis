# ADR-016: Google Authと本人参照のみのRLS

## 背景と課題

Issue #15はGoogle OAuth → Supabase Auth → JWTを唯一のログイン経路とし、個人データの所有者以外のアクセスを拒否する。Issue #14の21表はRLS有効だがポリシーがなかった。Supabaseの既定ではクライアントロールにも表権限が付くため、権限と行ポリシーを両方定義する必要がある。

## 選択肢

- `profiles`をAuthトリガーで作る: 行の欠落を防げるが、トリガー失敗がサインアップを止める。
- 認証後にAPIで作る: Authとアプリの障害を分離できるが、初期化失敗時の再試行が必要。
- 個人表を直接更新可能にする: 画面から扱いやすいが、プロフィール版の原子的確定と整合させにくい。
- 本人の直接参照のみ許し、変更と共有データはAPIに閉じる: 権限が小さいがAPI実装が必要。

## 決定

ユーザー判断により、Google以外のログイン経路をSupabase設定で無効にし、APIでも検証済みユーザーのGoogle identityを確認する。`profiles`はログイン後の`POST /api/v1/me/profile`で、認証済み本人のIDだけを用いて冪等に作る。Webにはpublishable keyのみ、管理操作にはサーバー専用secret keyを使う。

クライアントロールの全表権限を取り消し、`authenticated`には現行個人10表のSELECTのみを付与する。各SELECTポリシーは`auth.uid()`と所有者を比較し、子表は親をたどる。`anon`と共有11表は直接参照・更新不可。新規表の既定権限も拒否側に倒す。共有データのサーバー書込と本人データの変更は、後続IssueのAPI/transactionで実装する。

## メリット・デメリット

表権限とRLSの二重制限で、所有者の取り違えや新規表の偶発的公開を防ぎやすい。一方、ログイン直後のAPI初期化が失敗した場合は再試行が必要で、画面からの直接更新はできない。Google providerの設定はリポジトリのSQL migrationでは配布できないため、環境ごとの確認が必要。

## 見直し条件

追加のログイン方式、クライアント直接書込、共有データの直接公開、匿名サインインを要求する場合は、Auth設定・RLS・API契約・権限テストを同時に見直す。大学所属はGoogle identityのみでverified扱いせず、Issue #38で別に扱う。
