# ADR-049: 隣接する2つのanchorの間と読める軸を「範囲」として記録し、両端で比較する

> 状態: 決定（2026年10月02日）。ADR-044（全文脈の評価）、ADR-048（求人ページ全体の理解）を前提にする。

## 背景・課題

実際のJevで、Money Forwardの求人5件（hrmos）を評価した。不明になった軸19件のうち13件は、次の状態だった。

- 根拠のfragmentは確かにある（grounding 1.00）。
- 判定が隣接する2つのanchorに割れている（例: 50が0.50、100が0.48）。
- 同じページで3回実行しても、確率はほとんど変わらない。最上位は50と100の間で入れ替わった。

つまり、「書いていない」のではなく、「書いてあることが0/50/100の1点に決まらない」状態だった。これを「不明（書いていない）」と同じに表示すると、利用者を誤解させる。一方、最も確率の高いanchorを採るのはコイン投げと同じで、推測になる。閾値を下げるのも同じ理由で行わない。

## 決定

1. **crawler**（`context-judgement.ts`）:
   - 次の条件をすべて満たす時は、`range`（`anchorValue`=下端、`anchorMax`=上端）として根拠付きで記録する。
     - どのanchorも単独では確信がない。
     - 根拠の位置が確か（grounding 0.8以上、根拠あり）。
     - 隣接する2つのanchor（0-50か50-100）の確率の合計が0.8以上で、それぞれが0.15以上。
   - 1つのanchorに集中しているのに確信だけが低い判定は、範囲に広げず`unknown`のままにする。
   - 隣接しない割れ方（0と100）も`unknown`のままにする。
2. **DB**（`20261002104119_axis_range_observation`）:
   - `evaluated_axis_values.anchor_max`、`match_axis_results.observed_anchor_max`と`difference_max`を追加する。
   - CHECKは、隣接する範囲だけを受け付ける。比較結果は、両端の差と矛盾しないものだけを受け付ける。
   - NULLを比較すると条件が成立しない（CHECKを通ってしまう）ため、範囲の条件はすべて`is not null`付きで書く。
3. **domain**（`match-axis.ts`）:
   - 範囲は両端で比べる。両端とも希望から25以内なら`close`、近い方の端でも25を超えれば`different`、それ以外は`partial`（「一部近い」）とする。
   - 2つのanchorの間のどこかを推定することはしない。
   - `difference`は最小の差、`differenceMax`は最大の差とする。
   - 算法の版を`match-engine-v3`にする。
4. **表示**: 求人側を「50〜100」の区間として描き、「一部近い」の意味を文で説明する。集計（結果画面・共有ページ・OGP）では、「一部近い」を近い・不明とは別に数える。

## 結果（実Jev、同じ5件）

| | 変更前 | 変更後 |
|---|---|---|
| 不明 | 19 | 9（うち7件はオープンポジション） |
| 範囲 | 0 | 10 |
| known | 12 | 12（境界付近の1件は実行ごとに揺れる） |

## メリット

- 「書いていない」と「書いてあるが幅がある」を区別できる。
- 範囲でも、両端がどちらも近い、または両端とも遠い場合は、推測なしに判定できる。

## デメリット

- DB・domain・contract・UIの変更が大きい。
- `partial`という新しい比較状態が増える。
- 分析履歴の集計（`list_analysis_history_page_v2`）は、まだ`partial`を数えていない（残課題）。

## 見直し条件

- `range`の割合が高すぎる場合: anchorの定義（rubric）があいまいな可能性がある。rubricの版を上げて定義を見直す。
- 範囲の判定と人の判定が食い違う例が出た場合: 0.8と0.15の閾値を較正する。
