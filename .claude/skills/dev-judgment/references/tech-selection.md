# 技術選定と版の選び方

言語・フレームワーク・ライブラリ・DB・インフラ・外部サービスを選ぶとき、追加・更新するときに読む。

## 本人の方針（2026-11-03）
- **その場に最適な技術を選ぶ。** 本人や AI が慣れているか、好きかは判断の軸に入れない。
- **版は、その時点の最新の安定版を使う。** 古い版を「知っているから」選ばない。

出典: 本人の回答（2026-11-03）。Vault の `06-Personal/technical-skills-and-principles.md` にある「主軸にしたい技術」はキャリアの方針で、選定の軸ではない。

## 1. 条件を先に書く
選ぶ前に、この場の条件を書き出す。条件が書けない技術選定は、まだ比べられない。
- 何を解くか（機能・扱うデータ・量・応答の速さ）
- 動く場所（端末・ブラウザ・サーバ・Edge・オフライン）
- 費用の上限、運用する人と手間、どこまでの障害を許すか
- 寿命（使い捨ての試作か、続けて育てるか、公開するか）
- **今あるもの**：既存のリポジトリの言語・依存・CI・データ。乗り換えや混在のコストは、この場の条件として比べる（慣れの話ではない）

## 2. 候補を広く洗い出し、絞ってから比べる
思いついた2つだけで比べない。AI は有名なもの・自分の提案に出やすいものに偏るので、まず広げてから絞る。

**洗い出す**（数の上限は決めない。普通は5個以上出る）：
- 同じ種類の主な選択肢（例：DB なら RDB・ドキュメント・KV・組み込み）
- やり方そのものが違う案（自前で作る／マネージドサービス／ライブラリ／作らずに済ませる）
- 標準ライブラリや既存の依存で済ませる案
- 記憶に無い新しい選択肢：公式の資料・パッケージレジストリ・最近の比較記事で「今の時点で」探す（§3）

**絞る**：§1 の条件に合わないものを外す。外したものには理由を1行ずつ付けて残す（「外した: X — オフラインで動かない」）。理由が「知らない」「有名でない」なら外さない。

**比べる**：残ったものを全部、下の観点で比べる。数で切らない。残りが多すぎて比べきれないときは、決め手になる観点（§1 で一番重い条件）で先に順位を付け、上位を詳しく比べ、それ以外は順位の理由を1行書く。

| 観点 | 見ること |
|---|---|
| 条件への適合 | §1 の条件を満たすか。満たさないものは外す |
| 正しさ・安全 | 型安全性、入力の検証、認証・認可、既知の脆弱性 |
| 保守 | 開発が続いているか（最新リリースの日付、Issue への対応）、互換を壊す頻度、ライセンス |
| テスト容易性 | 差し替え・モック・ローカル実行のしやすさ |
| 性能・費用 | 測った値か、公式の値（前提つき）。推測で「速い」と書かない |
| 運用 | 監視・デプロイ・障害時の戻しやすさ、運用の手間 |
| 依存の重さ | 増える依存の数、ビルドや配布への影響。標準ライブラリや既存の依存で済むなら、それも候補に入れる |

観点の重みは §1 の寿命で変える（試作なら作る速さ、公開するものなら保守・安全・運用）。

## 3. 記憶ではなく一次資料で確かめる
AI の知識は古いことがある。次のことは、作業の時点で公式の資料（公式サイト、リリースノート、パッケージレジストリ、GitHub のリリース）で確かめ、確かめた日付と出典を書く。
- 最新の安定版の番号と公開日
- 保守が続いているか、非推奨・移行先の案内が出ていないか
- 料金や無料枠（時点つき）
- 対応する実行環境（言語やランタイムの版、OS）

確かめられなかったら「未確認」と書く。記憶の版番号を確かめたことにしない。
差が小さくて決めきれないときは、小さく試して測る（最小の実装、ベンチマーク、ビルドが通るか）。

## 4. 版の選び方
- 既定は**最新の安定版**。beta・rc・canary・nightly などのプレリリースは使わない（それしか条件を満たさないなら、理由を書いて本人に戻す）
- LTS がある技術（Node.js、Java など）は、最新の LTS を安定版とみなす
- 版は固定する（ロックファイル、正確な版の指定）。`latest` や範囲指定のまま放置しない
- 既存のリポジトリで依存を足すときも、その依存は最新の安定版。ほかの依存と両立しないときは、両立する中で最も新しい版にし、理由を書く
- 古い版を使い続けている依存を見つけたら、今回の作業と同じ PR では上げず、報告に書くか別のタスクにする（1 PR = 1 観点）

### 最新の安定版にしない場合（例外）
最新の安定版で、機能が静かに壊れる・ほかの依存と両立しない・必要な機能がなくなる、と確かめられたときだけ。
- 何が壊れるか（確かめた方法）、使う版、**いつ見直すか**（上流の修正、次のリリースなど）を残す
- 例：Expo SDK 58 で Firebase の初期化が壊れる恐れがあり、更新を保留した（gojuon-minesweeper PR #75、Vault の `06-Personal/github-pr-issue-lessons-2026-10.md`）

## 5. AI が決めるか、本人に戻すか
- §1 の条件がそろっていて、§2・§3 で1つに決まる → AI が決める（dev-judgment §2）
- 費用の上限・運用する人・寿命など、§1 の条件が本人にしかわからない → 戻す（dev-judgment §3）。そのあいだに、洗い出しと比較表を作っておく
- 有料のサービスの契約、クラウドの資源を作ること → 必ず止まる（dev-judgment §4）

## 6. 残し方
新しい技術を入れる、主要な技術を入れ替えるときは ADR、それ以外は PR 本文に書く。

```
背景と条件: 〈§1 の要点〉
洗い出した候補と外した理由: 〈X — 理由〉…
比べた候補: 〈A / B / C …〉
比較: 〈§2 の観点で、決め手になった差〉
採用: 〈A〉 〈版〉（〈確かめた日付と出典〉）
欠点: 〈A の弱いところ〉
見直す条件: 〈何が変わったら選び直すか〉
```
