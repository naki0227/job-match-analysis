# ADR-028: 軸別DecisionEngineの根拠IDとunknown

## 背景・課題

Issue #22では公開文書の観測値を8軸へ変換する。JevのScoreは本人の希望0〜100と同じ尺度ではなく、Jev応答はDBの出典行IDを直接返さない。候補にない根拠を作らず、不確実性を保持する契約が必要。

## 選択肢

1. Jev Scoreを0〜100に線形換算する。簡単だが尺度の根拠がなく、既存仕様に反する。
2. 出典候補ごとに固定アンカー0/50/100/noneのChoiceを問い、質問IDと候補IDをアプリ側で対応付ける。根拠の出所を検証できるが、候補の選び方と呼出し量を管理する必要がある。
3. Jevに軸値と自由記述の根拠をまとめて生成させる。呼出しは少ないが、存在しない引用を検出しにくい。

## 決定と理由

2を採用する。DecisionEngine入力にはカタログ/ルーブリック版、評価対象scope、軸の3アンカー、文書番号・位置・短い抜粋・候補IDを渡す。出力は軸ごとの`known`/`unknown`/`conflicting`、アンカー値、入力に存在する根拠候補ID、実モデル版、評価器版を返す。候補がなければJevを呼ばず`unknown`。Choiceのconfidenceと選択肢のprobabilityが共に0.8以上で、明示的なアンカーを選んだ場合だけ`known`候補とする。異なるアンカーが残れば`conflicting`。0.8は較正済みの正答保証ではなく、`jev-choice-v1`の保守的な保留閾値である。

本文はJevの`state`へ未信頼データとして分離し、質問側の命令は固定する。メール・電話・典型的なAPIキー形式を送信前に伏せ、プロフィールや認証情報を入力型に含めない。提供者の型外Choiceは拒否する。429/timeout/通信/5xxは一時失敗としてworkerに再試行を委ねる。Fakeは同じ入力・出力型を使い、CIで外部APIを呼ばない。

## メリット・デメリット・見直し条件

根拠IDを既知の候補に限定でき、Jev Scoreを軸値と混同しない。候補の抽出精度、名前などの個人情報の除去、モデルの誤分類はこの契約だけでは保証できない。実文書からの候補生成・DB評価保存・共有評価の再利用は後続の#22作業で接続し、実ページの評価・較正結果で閾値とルーブリック版を見直す。候補数と抜粋文字数の上限は費用に関わる運用入力として必須にし、値はここで固定しない。
