# ADR-048: 求人ページ全体を読んで根拠付きで構造化し、その後に希望と比較する

> 状態: 決定（2026年10月02日）。ADR-021/026/034（取得境界）、ADR-044（全文脈の評価）を前提にする。

## 背景・課題

Money Forwardの求人（`hrmos.co/pages/moneyforward/jobs/0004175`）では、元ページに「年収600万円〜1600万円」、複数の勤務地、週2日の出社必須が書かれている。それなのに本番の結果は「給与: 求人ページから確認できず」で、8軸も「0近い / 1相違 / 7不明」だった。実データで追い、次の原因を確認した。

1. **ブラウザ描画で、ページ自身のscriptを拒否していた。** browser boundaryは、すべてのsubresourceにページ本体用の1 MiB上限を適用していた。hrmos.coは給与欄を2.1 MBの自社script（`sg.published.libs.js`）で描画するため、このscriptが拒否され、給与の`<dd>`は空のままだった。静的HTMLには給与がhidden inputにしかない。
2. **描画が不完全でも気づけなかった。** 抽出文字数が100文字以上あれば「十分」と判定しており、必要なscriptを拒否したことは記録されていなかった。
3. **ラベルと値が別のfragmentに分かれていた。** `dt`「年収」と`dd`「600万円〜1600万円」、`th`「働き方」と`td`の本文が別fragmentになっていた。ラベル前提のparserは、全文を対象にしたfallbackでしか読めず、根拠には全文の先頭（「募集背景 …」）が保存されていた。
4. **200文字で語の途中から切っていた。** 区切りのない長い表は機械的に切られ、`週3以上の出社推奨（会社、業`のように条件の途中で切れていた。fragmentには、どの見出しの下の文かという情報もなかった。
5. **8軸が不明になる理由は2つあった。** 1つは、配属で業務が変わるオープンポジションでは、書かれていないこと自体が正しいこと。もう1つは、細切れで文脈のない74 fragmentを1回で判定していたため、根拠の指し方がぶれ、0.8の閾値を超えなかったこと。閾値を下げるのは推測を増やすだけなので、行わない。

## 決定

**unknownを減らすために推測しない。ページに書いてあることを、今より落とさずに使う。**

1. **取得**（`browser-boundary.ts`、`url-policy.ts`の`BROWSER_LIMITS`）:
   - ページ本体の上限は1 MiBのまま。描画に使うsubresourceは、1件4 MiB、1ページ合計16 MiB、64 requestまでとする。
   - URL・DNS・robots・GET限定の検査は変えない。
   - 拒否したdocument/script/xhr/fetchの数を`blockedRendering`として数え、`job_match.source_fetch.pages{render=partial}`で計測する。
2. **抽出**（`source-extractor.ts`、`html-v3`）:
   - 表の行（`th`+`td`）と`dt`+`dd`を1つのfragmentにする。
   - 各fragmentに、直前の見出しまたは行ラベルを`section`として付ける。`section`はページの文言であり、DOMの経路ではない。
   - inlineの`display:none`は読まない。
   - fragmentは今までどおり、見える本文の全体を順番どおりに覆う（semantic tag以外の部分はgap fragmentとして残す）。
3. **文脈**（`context-fragments.ts`、`context-fragments-v5`）:
   - 件数や総文字数による選別・切り捨てはしない（ADR-044のまま）。
   - 根拠の長さの上限を超える文だけを分割する。切る位置は文末または箇条の記号（■・※↓【 -）、なければ空白とし、語の途中で切るのは空白のない連続が上限を超える時だけにする。分割で失われる文字はない。
   - Jevには各fragmentの`section`も渡す。
4. **求人の事実**（`deterministic-parser.ts`＋`job-fact-patterns.ts`、`job-facts-v7`）:
   - 値を読む順は、それを書いているfragment → ラベルと値が同じ見出しの下にあるsection → 求人全文。
   - 全文から読んだ時も、根拠は値を書いている最短の連続fragmentにする。
5. **求人の見出し単位の内容**（`job-sections.ts`）:
   - 「仕事内容・役割」「求める人物・経験」「働き方」を、ページ自身の見出し・行ラベルで分類する。本文の語では分類しない。
   - 該当するfragmentを原文のまま引用として保存する。要約はしない。
6. **Jevへの位置の質問**（`located-facts.ts`）:
   - parserが読めなかった事実（給与・勤務地・出社日数・雇用形態）と、見出しで見つからなかったsectionだけ、同じJev呼び出しで「どのfragmentに書いてあるか」を選択肢（`f1…fN`/`none`）で尋ねる。
   - 値は、指されたfragmentの原文からparserと同じ種類のpatternで読む。Jevに値を作らせない。
   - 月給・時給を年収として読まない。
   - 採用の条件は軸の根拠と同じ（grounding 0.8、1 fragmentあたりの確率0.1）。
   - こうして得た値には`method: "jev"`を付ける。
7. **保存と表示**:
   - `evaluation_job_facts`に`duties`・`requirements`・`workStyle`を追加する（`20261002053703_job_sections_facts`）。
   - 引用と抜粋からは、Jevへの送信時と同じ規則でメール・電話・秘密情報を除く（`redaction.ts`）。
   - 結果画面は、求人概要（各事実の原文付き）→ 仕事内容・役割 → 働き方 → 求める人物・経験 → 希望条件との比較 → 8軸、の順に表示する。前半は「求人に書いてあること」、後半は「あなたとの比較」として分ける。

## 採用理由

- 失われていた情報は、どれもページに書いてあった。描画・抽出・分割で失わないようにするのが、推測を足すより先にやるべきことである。
- 見出しによる分類と、選択肢だけを使うJevの位置特定は、どちらも原文を指す。どの値にも、ページ上の根拠が必ずある。
- 見出しも根拠もない時は、今までどおりunknownになる。

## メリット

- 給与・勤務地・出社条件の取りこぼしが減る。根拠が実際の記載箇所を指す。
- 求人の内容（仕事内容・求める人物・働き方）を、比較の前に原文で確認できる。
- 不完全な描画を計測できる。

## デメリット

- 描画のための通信量の上限が増える（1ページ最大16 MiB）。
- Jev呼び出しに、位置の質問が最大7問増える。呼び出し回数は1回のまま。
- 見出しの語彙に頼るため、見出しのない求人ではJevの位置特定に頼る。
- `evaluation_job_facts`の行が増える。
- 抽出・文脈・parserの版が変わるため、既存の評価は再利用されず、次の解析で作り直される。

## 見直し条件

- `render=partial`の割合が高い場合: 拒否の理由（robots・size・method）を分けて計測し、上限や方針を見直す。
- 月給・時給の求人が多い場合: 給与の期間（`period`）を年以外にも広げる（contractとmatch engineの変更が必要）。
- 見出しの語彙で分類を誤る例が出た場合: 語彙を追加するか、Jevによる位置特定を優先する。
