# ADR-020: 診断プロフィールの読取と版保存

## 背景と課題

Issue #25では本人の診断を画面から保存・再読込する。既存の`commit_career_profile` RPCは版と子行を原子的に確定し、個人表のSELECTには本人RLSがある。APIで両者をどう接続するかを決める。

## 選択肢

- 画面からDBを直接読む/書く: APIは小さいが、保存RPCはservice_role専用なので書込権限を広げる必要がある。
- サーバーのsecret keyで読取と保存を行う: 実装は単純だが、読取がRLSを迂回する。
- 読取は本人JWT付きpublishable client、保存はサーバー専用RPC: API認証に加え、読取をDBのRLSでも制限できる。クライアントの作り分けが必要。

## 決定

APIはBearer tokenを`auth.getUser(token)`で検証し、Google identityを確認する。GETは同じJWTをpublishable clientのAuthorizationへ渡し、本人の最新completed版を取得する。子行は取得した版IDだけで読み、共有Zod契約で応答を検証する。PUTは共有Zod契約で8軸・希望職種・制約・期待版・冪等キーを検証し、検証済み本人IDだけをservice_role専用RPCへ渡す。クライアントからuserIdや版IDを受け取らない。

未回答は入力中の画面状態として保持し、確定保存には8軸すべての回答が必要。`importance=0`は有効な回答とする。初回保存は201、後続版は200。再送は同じ冪等キーを使う。競合は409で再読込を求め、既存確定版を上書きしない。

今回の版確定ユースケースは既存DB関数が原子性と競合制御を担う。APIは認証・契約検証・DB呼出し・HTTP変換だけに留めるため、`packages/application`に単なる中継層を作らない。複数のportを組み合わせるユースケースが生じた時点で独立パッケージを作る。

## メリット・デメリット

GETにはAPI認証とRLSの両方が効き、PUTは既存の原子的保存・版競合制御を再利用できる。一方、最新版と子行の読取は複数のHTTP問い合わせになる。最初に版IDを固定して以後の問い合わせに使うため、後続版の同時保存があっても取得した版の内容は変わらない。

E2Eには`@playwright/test`を開発依存として追加し、ローカルChromeのheadless実行でログイン済みfixtureから保存・再読込を検証する。手動操作だけでは回帰を自動検知できないため採用した。ブラウザのバージョン差に伴う保守と実行時間が増えるので、通常CIには現時点でE2E実行ジョブを追加しない。

## 見直し条件

読取回数が実測で問題になった場合は、RLSを維持する単一読取RPCまたは埋め込みSELECTを検討する。プロフィールの部分保存が必要になった場合はdraftの契約を別に設計し、completedの全8軸制約を緩めない。
