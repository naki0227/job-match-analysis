# 開発の始めと終わり

本人（naki0227）のグローバル開発ルールを、毎回の手順にしたもの。途中で「どちらにするか」迷ったら `dev-judgment` を使う。
これは本人の開発の流れ（`dev-lifecycle`）の 8〜9（実装・テスト）を中心にした手順。新しい機能や改善を考えるところから始める依頼、解決策の形で来た依頼（「〇〇を足して」）は、先に `dev-lifecycle` で課題と作るものを確かめる。

## 作業の大きさを決める

| 大きさ | 目安 | 始め | 終わり |
|---|---|---|---|
| 小 | 1〜2ファイル、振る舞いが明らか（誤字、文言、設定値） | 目的と CI のコマンドだけ確かめる | 関係するチェックを回し、差分を読む |
| 中 | 振る舞いが変わる。テストを足す | `references/start.md` を全部 | `references/finish.md` を全部 |
| 大 | DB・API・認可・依存・複数リポジトリ・運用に影響 | 中に加えて、影響範囲と戻し方を先に書く | 中に加えて、ADR と戻し方の確認 |

迷ったら1段大きいほうにする。手順を飛ばしたら、その理由を報告に1行書く。

## 始め（詳しくは `references/start.md`）
1. 目的：だれの何を解決するか。期待する動作（正常・異常）と、変えない範囲
2. 品質の基盤：CI の定義と、ローカルで回すコマンド。今すでに落ちているものがあるか
3. Vault：このリポジトリのノートと関連ノートを読む（`CLAUDE.md` の手順）
4. 縦に追う：入口 → 呼び出し → 変換 → I/O・DB → 状態の変化 → エラーと後片付け
5. 横に比べる：同じ役割の実装・テスト・helper を2〜3件
6. 決めることを書き出し、`dev-judgment` で「AI が決める／人に戻す」に分ける

## 終わり（詳しくは `references/finish.md`）
1. 自分が書いたのではないつもりで、最終の差分を読む
2. 反例で壊す：テストが誤った実装で本当に落ちるか、紛らわしい入力・権限の欠け
3. チェックを回す：対象のテスト → 関係するテスト → format / lint / 型 / build
4. 状態の言葉を正確にする（`references/finish.md` の表）
5. 作業報告書と Todo（このリポジトリの方式で）、Vault（再利用できる学びがあれば）
6. 報告：変更 → 確認（コマンドと成否）→ やっていないことと理由 → リスク・残り → 次の作業
