# ADR-015: 希望職種をCareerProfile版に保持する

## 背景と課題

診断の最初に希望職種を聞く要件が確認された。既存のCareerProfile版には8軸と必須条件しかなく、DBのプロフィール履歴にも希望職種が残らない。`docs/design.md`の「職種など」はMVPで確定した3つのHard Constraintと混同し得る。

## 選択肢

- CareerProfileVersionに必須の希望職種リストを保存し、DBでは順序付き子テーブルを用いる。最初のUI入力は1件。職種判定は別途仕様化する。
- CareerProfileVersionに単一の職種文字列を保存する。実装は簡単だが、複数希望への拡張でschemaと契約が変わる。
- プロフィール外の検索条件にする。プロフィール版を小さく保てるが、再評価時に当時の希望が追いにくい。

## 採用した案と理由

ユーザーの判断により最初の案を採用。希望職種は自己申告のプロフィール情報として版ごとに保持し、改訂時は新しい版を作る。職種名は入力文字列として保持し、空白と同一表記の重複を検証する。現時点で職種分類への正規化や求人との一致を推測しない。

## メリット

- 過去の診断時の希望職種を追える。
- UIが1件から始まっても複数希望へschema変更なしで拡張できる。
- まだ定義されていない職種照合をHard Constraintへ混入させない。

## デメリット

- 子テーブルとJOINが増える。
- 表記揺れがあるため、職種名だけで求人の適合を自動判定できない。
- DB単独ではcompleted版に1件以上の子行があることを通常のFK/CHECKだけで保証できない。確定処理の原子性はIssue #16で扱う。

## 見直し条件

求人の職種分類と対応づける仕様を決めた時、または希望職種を必須除外に使う要件が確定した時に、新しい判断とテストを追加する。
