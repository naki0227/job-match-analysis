# ADR-023: 分析履歴を本人のMatch結果から取得する

## 背景と課題

Issue #27の画面は保存・お気に入り操作ではなく「分析済み企業」を示す。Issue #17の`user_saved_jobs`と`list_saved_jobs_page`は、操作しないと行が作られず、この仕様と食い違う。一方、Match結果には本人、求人評価、プロフィール版、作成日時が残る。ADR-018の1 RPC、keyset cursor、N+1回避は引き継げる。

## 選択肢

- `match_results`を元にする: 分析完了と同時に一覧へ現れ、再分析の履歴も残る。求人ごとの最新結果を選ぶSQLが必要。
- 分析履歴専用の子テーブルを追加する: 一覧は単純になるが、Matchとの二重書込み・不一致を管理する必要がある。
- `user_saved_jobs`を自動追加に変える: 既存SQLを流用しやすいが、保存操作を廃止した後も意味の違う表が残る。

## 決定

本人の**求人を対象としたMatch結果の確定**を、個人の分析履歴への追加とみなす。共有評価だけでは個人のMatchは完成していないため一覧には出さない。求人ごとに`(match_results.created_at DESC, id DESC)`の先頭1件を一覧に表示し、古いMatch行は削除せず詳細画面から参照できる版として保持する。同時刻にはIDで全順序を付ける。会社単位のMatchと、Matchのない共有求人評価は含めない。

`list_analysis_history_page`は検証済み本人IDを受け取るservice_role専用の`SECURITY INVOKER` RPC。求人ごとの最新Matchを選んだ後、Match日時とIDのkeyset cursorで最大100件（次ページ判定のためDBは`limit+1`件）を返す。表示する求人評価は**そのMatchが参照した評価版**、会社評価は取得時点の最新共有版とする。API repositoryは1ページを1 RPCで読み、DB応答を検証する。HTTP公開、フィルタ、詳細画面はIssue #27で扱う。

旧テーブルに行があればmigrationを停止する。旧ブックマークは分析済みと同義ではないため自動変換しない。空であることを確認できた環境にのみ新migrationを適用し、旧表・RPCを削除する。既存migrationは履歴として残す。rollbackは旧表・RPCを空で再作成し、旧行の復旧には事前バックアップが必要。

## メリット・デメリット

保存操作とMatch結果の二重管理がなくなる。過去のプロフィール版と求人評価版を保持でき、一覧は1回のDB往復で取得できる。一方、求人ごとの重複除去は本人のMatch件数が増えると高コストになり得る。会社の最新評価は過去Matchに固定された版ではないため、詳細では当時の評価と区別して表示する。

## 見直し条件

Match件数増加で一覧のEXPLAIN・実測が目標を外れた場合、履歴の集約表や索引を検討する。企業ごとに複数求人をまとめる表示、分析中ジョブを一覧に出す仕様、フィルタ、カーソルのHTTP表現はIssue #27で決める。
