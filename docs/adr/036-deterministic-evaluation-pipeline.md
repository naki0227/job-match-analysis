# ADR-036: 決定的な求人情報を先に解析し、残りをJevで判定する

## 背景・課題

Issue #43では年収・勤務条件など明示的な情報までJevへ送ると、費用と判定揺れが増える。従来の評価は8軸をすべてDecisionEngineへ渡し、評価方法と求人条件を版に保存しなかった。

## 選択肢

1. 全項目をJevへ送る。実装は単純だが、明示値まで外部判断に依存する。
2. 公開本文の明示表記を決定的に抽出し、根拠のある軸だけルールで確定する。残りの候補だけJevへ送る。処理と版管理は増えるが、過剰なJev呼出しを避けられる。
3. ローカルLLMへ移す。外部呼出しを減らせる可能性はあるが、GPUと運用負担をMVPに持ち込む。

## 決定と理由

2を採用する。求人scopeの明示表記だけから年収範囲、勤務地の都道府県名、フルリモート、週の出社日数、フレックス、JobPostingの職種、明示された技術スタックを抽出する。月給から年収への換算や、曖昧な勤務地・出社日数の推測は行わない。勤務地の名称からプロフィール用コードへの正規化と必須条件判定は別の判断とする。

8軸のうち出社形態と勤務時間は、選択済みの短い根拠候補に明示された場合だけルールで確定する。矛盾する記述はconflictingとし、Jevへ再解釈させない。それ以外の根拠候補だけをJevへ渡す。候補がない軸はunknownとし、外部呼出しを省く。評価方法は軸ごとに保存し、求人条件は評価IDを親とする子行に保存する。既存RPCを呼ぶv2 RPC内で両者を同一トランザクションに確定し、同じ評価版を再利用する際は両者の一致を確認する。

候補選択器は短い明示的な出社表記を通すため`axis-keywords-v2`とする。parser、rule、selector、Jevの版を評価器版に含め、source set hashには従来どおりURL・本文hash・取得日時・抽出版・候補を含める。

## メリット・デメリット・見直し条件

明示的な勤務条件を外部推論に依存せず、判定方法と根拠を追跡できる。求人ページの表記揺れには保守的にunknownを返すため、抽出率は限定的。候補選択の上限で根拠が落ちる場合もunknownとなる。実ページのfixtureで誤判定・取りこぼしが判明した時に、parserとruleを版付きで拡張する。個人情報の完全検出と引用・二次利用条件は別途確認する。
