# 始めの手順（中・大の作業）

## 1. 目的と期待動作
- だれが、どんな場面で、何に困っているか。依頼の文だけでなく、Issue・PR・Design Doc・README の目的と合っているか
- 入力・出力・正常系・異常系。**変えない範囲**（公開 API、保存形式、既存の利用者）
- 依頼の手段では目的が満たせないと思ったら、`dev-judgment` §5（反対するとき）

## 2. 品質の基盤を先に知る
```sh
ls .github/workflows/ 2>/dev/null; cat Makefile package.json 2>/dev/null | head -80
git log --oneline -10
```
- CI が何を回し、何がマージを止めるか。ローカルで同じことを回すコマンド
- 今の状態で一度回し、**すでに落ちているもの**を記録する（自分の変更のせいにしない・混ぜて直さない）
- CI が無く、続けて開発するリポジトリなら、機能の前に最小の CI を別のコミットで入れる
- CI が回せない環境なら、代わりに何で確かめるかと、確かめられない範囲を先に決める

## 3. Vault
- `CLAUDE.md` の「共通知識基盤」の手順に従う。今回の技術名・問題の種類・設計上の関心事で `rg -i` する
  ```sh
  rg -il "<技術名>|<問題の種類>" ../personal-knowledge --glob '*.md'
  ```
- 過去の同じ問題の、採った案と**採らなかった理由**を読む。記録は `source_date`・`status` を見て、今の実装はコードで確かめる

## 4. 縦に追う
入口 → 呼び出し → データの変換 → I/O・DB → 状態の変化 → エラー・後片付け。
- だれが呼び、何を返し、何が保存・送信されるか
- transaction、rollback、retry、timeout、後片付け、監視への通知がどこで起きるか
- 今の振る舞いを守っているテストはどれか
- 他のサービスやリポジトリへ渡るなら、必要な範囲で境界を越えて読む

## 5. 横に比べる
```sh
rg -n "<型名|関数名|定数>" ; rg -ln "<似た責務の語>" --glob '!node_modules'
```
- 同じ役割の実装・テスト・suite・factory・mock を2〜3件。過去の PR は最終の状態と変えた理由まで
- テーブルや endpoint を足す前に、既存の schema・route・migration を見る
- 既存のやり方と違うことをするなら、その理由を言えること。言えないなら既存に合わせる

## 6. 決めることを分ける
決めることを箇条書きにし、`dev-judgment` で振り分ける：
- AI が決める → 進めて、判断を残す
- 人に戻す → まとめて1回で聞き、答えに左右されない部分は先に進める
- 必ず止まる操作 → 実行の直前に確認する

## 7.（大のとき）影響と戻し方を先に書く
- 呼び出し元、公開 API、DB、認証・認可、他サービス、既存の利用者、移行と運用
- 戻し方（revert で戻るか、データの移行が要るか）と、段階的に出せるか
