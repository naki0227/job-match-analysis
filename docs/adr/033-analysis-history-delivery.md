# ADR-033: 分析済み企業の絞り込みと離脱後の反映

## 背景・課題

ADR-023では本人の求人Matchを履歴の元にした。ADR-032のWebによるMatch作成だけでは、解析を依頼して画面を閉じた場合に共有jobが完了しても本人のMatchが作られない。Issue #27は保存操作なしの一覧、絞り込み、ページング、版と鮮度の表示を求める。

## 選択肢

1. ブラウザ内に未完了依頼を保存する。実装は軽いが、別端末・データ消去・タブ終了時の保証が弱い。
2. 共有jobに本人IDを持たせ、worker完了時にMatchを作る。即時反映しやすいが、共有処理が個人情報とプロフィールに依存する。
3. 本人の依頼を別表に原子的に記録し、再訪時に未反映評価をMatchへ変換する。共有jobの責務を保てるが、再訪時の追加処理が必要。

## 決定

3を採用する。`request_personal_analysis`は従来の`request_analysis`を呼び、同じトランザクションで`user_analysis_requests`へ検証済み本人IDとjob/評価を記録する。個人表はRLSを有効にし、クライアント権限とポリシーを与えず、service_role専用とする。履歴の先頭ページを読む前に未反映評価を取得し、既存の`createMatch`ユースケースで最新の確定プロフィールと比較・保存する。同じ評価の保存は既存の一意制約で冪等。1回の取得で最大20件を反映する。プロフィールがないか軸版が合わない評価はMatchにならず、後のアクセスで再試行する。

一覧は`list_analysis_history_page_v2`の1 RPCで取得する。求人ごとの最新Matchを選んだ後に希望職種・判定で絞り、`recent`、近い件数、少ない不明件数の順にkeysetページングする。カーソルは絞り込みと並び順に紐付ける。当時のプロフィール版と求人評価IDを返し、重要な求人条件の`stale_information`または出典取得日の鮮度切れを警告する。総合点や保存ボタンは追加しない。

## メリット・デメリット

画面を閉じても本人の依頼がDBに残り、再訪時に結果が履歴へ入る。共有jobの公開範囲は変わらず、一覧の1/20/100件取得は各1 RPC。初回の未反映分は1件ごとに既存MatchユースケースのDB操作が必要で、20件超は次回の先頭ページ取得で続ける。Matchができない評価を履歴として表示しないため、プロフィール未保存時は希望条件の入力が必要。

## 見直し条件

未反映依頼の件数や再訪時の遅延が問題になれば、個人Match作成をバックグラウンド処理へ移す。本人がアプリを開かずに即時反映する要件が確定した場合も同様。共有jobの完了と個人Matchの可用性は監視対象として別に扱う。
