# ADR-029: 公開資料の根拠候補と評価入力の版

## 背景・課題

Issue #22のDecisionEngineは短い出典候補と8軸のアンカーを受け取る。HTML抽出本文をそのままモデルに渡すと、求人と会社の記述が混ざり、入力範囲と呼出し量も追跡しにくい。同一評価を再利用するには、候補の作り方と取得文書を識別する必要がある。

## 選択肢

1. 抽出本文全体を評価器に渡す。実装は単純だが、無関係な本文が増え、根拠位置を固定しにくい。
2. 段落を公開8軸の語で絞り、文ごとに出典位置と安定IDを付ける。根拠を追える一方、言い換えや複雑な文を見逃す。
3. モデルに候補抽出も任せる。表現の揺れに強い可能性があるが、抽出の再現性と引用の検証が難しく、追加呼出しが要る。

## 決定と理由

2を最初の候補生成として採用する。HTMLの求人・会社断片を分け、対応する軸語を含む短い文だけを選ぶ。候補には文書番号、scope、HTML位置、文、SHA-256のIDを付ける。メール・電話・典型的な秘密キーを含む文は候補から除く。候補数と文の最大文字数は呼出し側が正の整数で指定し、ここでは費用に関わる値を固定しない。長い文を途中で切ると引用が不正確になるため、上限を超える文は候補にしない。全軸に順番に枠を配分する。

8軸の公開資料アンカーは`docs/assessment-axes.md`の内容を`public-anchors-v1`としてコード化する。候補選択を`axis-keywords-v1`とし、Jev評価器版に選択器版を含める。評価入力のsource set hashには選択器版、scope、順序付きのURL・本文hash・取得日時・抽出版、および候補内容を入れる。候補順だけではhashを変えない。再取得は本文が同じでも別の時点の根拠として扱う。

## メリット・デメリット・見直し条件

入力候補と位置を再現でき、情報不足は`unknown`のまま残せる。語にない表現、表構造、文の切れ目がない記載は取りこぼす。文字列パターンによる個人情報除去は完全ではないため、実ページをモデルへ送る前の追加レビューが必要。実ページで候補の取りこぼし、混入、引用精度を確認し、選択器・アンカーを改訂する際は版を上げる。サイト別の利用条件と引用長の法的・運用判断は別途確定する。
