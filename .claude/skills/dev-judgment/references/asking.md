# 人に戻すときの書き方

本人は、短く、結論から、根拠つきの話し方を好む。前置き・謝罪・長い背景はいらない。

## 形

```
〈決めたいこと〉を決めるのに、〈足りない事実〉が要ります。
- A: 〈案〉 — 〈得〉／〈失〉
- B: 〈案〉 — 〈得〉／〈失〉
- …（残った案は全部並べる）
外した: 〈X〉（〈理由〉）、〈Y〉（〈理由〉）…
推し: A（〈理由〉）。〈足りない事実〉が〈こう〉なら B。
その間に、答えに左右されない〈作業〉を進めておきます。
```

- 見せるのは、条件で絞って残った案（数は決めない）と推し1つ。何がわかれば答えが変わるかを書く
- 外した候補も「外した: X（理由）」と1行ずつ添える。本人が外し方に異論を言えるようにする
- 質問はそれだけで読めるように書く（直前の調査結果を読んでいなくても、何を聞かれているかわかる）
- 調べてわかることを聞かない。すでに聞いた・答えをもらったことは聞き直さない
- 1回にまとめて聞く。小出しに何度も止めない

## 良い例と悪い例

悪い：「DB はどうしますか？」（何が決まっていないのか、AI が何を調べたのかがわからない）

良い：「履歴一覧の集計に索引を足すか決めたいです。今の計測では 1000 件で p95 95ms、目標 300ms 内です（job-match-analysis Issue #83 の値）。
- A: 今は足さず、1万件で測るタスクを残す — 書き込みの負担なし／件数が増えたら遅くなる
- B: 複合索引を足す — 読みが速い／書き込みと migration の手間
推し: A。利用者が1万件を超える見込みが近いなら B。」

悪い：本人しか知らない予算がわからないまま、勝手に「無料枠で収まる構成」を前提に作る。
良い：費用の上限を聞き、そのあいだに構成ごとの月額の見積もり（前提と時点つき）を作っておく。

## 戻さずに進めたときの書き方

報告に「判断: 〜／理由: 〜／採らなかった案: 〜／見直す条件: 〜」を残す（SKILL.md §6）。「念のため確認です」と、決め終わったことを質問の形にしない。
